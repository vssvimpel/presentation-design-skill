# Деловая презентация: методика, сборка и проверка согласованности

## Главная идея

Презентации рассыпаются не из-за дизайна, а потому что один и тот же факт (число, название
слайда, вывод) записан руками в нескольких местах: поправил в одном — остальные остались
старыми. Поэтому:

1. Каждое число живёт **один раз**, в реестре `facts.json`; в слайдах оно только
   отображается через `data-fact`.
2. Производные метрики (CPA, ДРР, доли, разницы) задаются формулой `derive`, а не числом.
3. Слова о направлении («вырос», «снизился») привязаны к факту через `data-trend`, и знак
   сверяется скриптом.
4. Названия слайдов, оглавление, нумерация и ссылки «слайд N» сверяются скриптом.
5. То, что скрипт проверить не может (логика выводов и рекомендаций), проверяется чтением
   по `references/consistency-checklist.md`.

Скрипт `scripts/check_deck.py` работает на голом Python 3.8+ (только стандартная
библиотека). Запускай его вместо «вроде бы проверил глазами».

Бренд: конкретные цвета и нарратив приходят из брендовой надстройки
(для «Ренессанс Страхование» — скилл `renins-brand-presentation`). Этот скилл задаёт каркас
и инструменты; значения бренда подставляй из надстройки, а если её нет — бери фирменные
токены Маркова (см. §1).

## 0. Главный принцип дизайна

Слайд не должен выглядеть как «сгенерированный ИИ»: нет равных по площади цветов,
кремовых фонов «по умолчанию», декоративных линий и слайдов с одним текстом.
Всё держится на доминанте, тонировке и связке с данными.

## 1. Палитра: роли вместо конкретных цветов

Разложи цвета бренда по РОЛЯМ (роли универсальны, оттенки — нет):

- **доминанта** — тёмный фон титула и финала;
- **основной текст** на светлом фоне;
- **светлая тонировка** — карточки, подложки;
- **приглушённый акцент** — второстепенные элементы;
- **разделитель** — тонкие рамки;
- **вторичный текст** — подписи, сноски;
- **резкий акцент** — только ключевые цифры/KPI.

Фирменные токены Маркова (дизайн v4, `static/styles.css`), если брендовой надстройки нет:

| Роль | Токен | Значение |
|---|---|---|
| фон страницы | `--page-bg` | `#F5F4F0` |
| поверхность | `--surface` | `#FFFFFF` |
| основной текст | `--text` | `#141413` |
| вторичный текст | `--text-secondary` | `rgba(0,0,0,0.5)` |
| разделитель | `--border` | `rgba(0,0,0,0.08)` |
| акцент | `--accent` | `#C87A5C` (терракота) |
| положительная динамика | `--success` | `#29AD49` |
| отрицательная динамика | `--error` | `#D4183D` |
| внимание | `--warning` | `#D97706` |
| тонировка | `--highlight` | `#E9E5FF` |

### Правило доминанты (обязательно)
- 60–70% площади — доминанта;
- 1–2 второстепенных (нейтральные/приглушённые);
- резкий акцент — не более 10–15%, только на цифрах и KPI.
- Никогда не раскрашивай блоки равным весом.

### Правило акцента: заливка, а не текст
Акцентные цвета обычно не проходят контраст как цвет текста. Ставь их **заливкой**
(чип, круг, карточка), а текст по ним — основным тёмным. Проверяй контраст по WCAG:
AA = 4.5, для заголовков AAA = 7.0, для крупного текста 3.0. Если цвет не проходит как
текст — это не повод его менять, это повод сделать его заливкой.

## 2. Архитектура слайдов

### Сендвич
- Титульный слайд — тёмный (доминанта).
- Контентные слайды — светлые.
- Финальный слайд — тёмный (возврат к доминанте).

### Порядок и роли
Порядок «вывод, затем доказательства» сохраняй. Роли слайдов задаются атрибутом
`data-role` (нужны для проверки ключевых фактов):

1. `title` — тема, период, продукт, вопрос отчёта, оглавление со ссылками (`data-agenda`).
2. `summary` — главный вывод: ответ в первых строках, 3–4 ключевые метрики, 2–3 вывода
   со ссылками на слайды-доказательства.
3. `method` — данные и допущения: источники, период, модель атрибуции, проблемы с данными,
   что считается предварительным.
4. `finding` — находки: один слайд на одну мысль, таблица или график, строка «что это значит»,
   уверенность. У каждой находки есть период и источник.
5. `recommendation` — действие, ожидаемый эффект, риск, уверенность, пометка о согласовании
   с юристами и комплаенсом, если речь о рекламе или условиях продукта.
6. `next` — что проверить дальше: какие данные запросить, какие гипотезы проверить.
7. `appendix` — определения метрик, длинные таблицы.

### Каждый слайд
- Kicker (надзаголовок мелким капсом) + заголовок.
- Обязателен визуальный элемент: иконка, диаграмма, фигура, крупная выноска.
  Слайда с одним текстом быть не должно.
- Ключевая цифра — крупная выноска, подпись под ней мелко.
- Сетка: 2 колонки / 2×3 / иконка+текст / крупная выноска / таймлайн.
  Чередуй компоновки между слайдами, не повторяй подряд.
- Лимиты на слайд: не более 7 пунктов, 12 строк таблицы, около 140 слов. Больше — дели
  слайд или выноси в приложение.
- Заголовок формулирует мысль словами, без чисел: «Поиск дешевле партнёров», а не «CPA
  поиска 800 ₽». Число в заголовке не обновляется скриптом и разойдётся с реестром.
- Единые термины на всём деке: если в одном месте «CPA», в другом не пиши «стоимость заявки»
  про ту же метрику.

### Мотив вместо полос
Не используй цветные полосы, подчёркивания, боковые панели, декоративные линии.
Вместо них — тонировка фона, тень карточки, иконка в цветном круге, крупная фигура
цифры. Это читается как дизайн, а не как шаблон.

## 3. Типографика
- Заголовки крупные (36–56px; в PPTX 24–36pt), текст мелкий (14–17px; 11–13pt),
  курсивный акцент на ключевых цифрах.
- Шрифт по бренду/дизайн-системе; если нет — без засечек. НЕ Georgia/Times.
- Padding слайда 56–72px, воздух между блоками 20–36px.
- Текст по левому краю, заголовки по центру/влево. Подписи — вторичным цветом.
- Проверка на перекрытие (до экспорта): заголовок 30–40pt занимает ~1,1–1,3″
  по высоте → график/картинку ставить не выше `y ≥ 1,8″` при заголовке в одну
  строку, иначе текст залезает под изображение. Координаты считай от реальной
  высоты блока, не «на глаз».

## 4. Сводный график — переиспользуемый приём
Один график вместо двух, когда нужны разные масштабы. Линии + столбцы, несколько осей.
- Линии — для динамики (бюджет, продажи). Столбцы — для относительной метрики.
- Разные шкалы → разные оси Y. Масштабные величины — на правую вспом. ось.
- Столбцы с закруглённым верхом: `itemStyle:{borderRadius:[6,6,0,0]}`.
- Легенда вниз (`bottom:0`, `itemGap:24`), нижний отступ сетки `bottom:44`,
  `containLabel:true` — чтобы подписи не наезжали.
- Цвета рядов: доминанта + акцент для линий; столбцы — приглушённый цвет.
- Значения над столбцами подписывай: зритель не должен оценивать высоту на глаз.

Когда приём не применять:
- метрики не связаны по смыслу — на одной картинке это читается как манипуляция;
- больше двух осей Y — сравнение теряется;
- точек меньше шести — линия вводит в заблуждение, бери столбцы.

## 5. Честность цифр (обязательный блок, если есть расчёт или прогноз)

### 5.1. Однозначность охвата каждой суммы
Цифра на слайде описывает ровно то, что написано в подписи — ни шире, ни уже.
Делать на этапе данных, до вёрстки: неверная подпись разойдётся по титулу, финалу и легендам.
1. Возьми каждую сумму и ответь: какие именно строки источника в неё вошли.
2. Найди колонку-признак принадлежности (кто платил / продукт / канал). Есть —
   разложи сумму по ней и проверь, нет ли статей, не относящихся к теме презы.
3. Колонки нет — не выдумывай разрез и не пиши «только». Подпись нейтральная:
   «сумма по источнику X» + отдельно то, что известно о составе.
4. Посторонние статьи есть — сузь агрегат до темы (укажи формулу отбора строк)
   либо вынеси отдельным слайдом, а не прячь в общую сумму.
5. Слова-маркеры риска: «только», «всего», «исключительно», «чистые». Каждое
   допустимо лишь тогда, когда строки-доказательство есть под рукой.

Проверочный вопрос перед вёрсткой: если открыть источник и попросить показать
строки, из которых сложилась цифра, — они найдутся, и все по теме?

### 5.2. Слайд допущений — отдельный и обязательный
Если есть прогноз, добавить слайд «Это прогноз, а не факт»: что взято из данных,
что задано вводной, что предположение. Каждое допущение — отдельная карточка.

### 5.3. Сценарии чувствительности
Если итог зависит от одной вводной (средняя стоимость дня, курс, норма расхода) —
дать 3 сценария низкий / базовый / высокий и показать разброс числом.

Границы бери из данных, а не подбирай:
- базовая — среднее по периоду;
- низкая — среднее с выбросами, сглаженными до стандартного отклонения;
- высокая — среднее с максимальным наблюдением.

Сглаживание выбросов. Выброс — наблюдение, отклоняющееся от среднего больше чем
на σ. Минус выбросов не выбрасывается: подставь на его место σ, чтобы сохранить
число наблюдений. Формула (выборочная): σ = sqrt( Σ(xᵢ − x̄)² / (n − 1) ).
Порог наполненности ряда — 15 наблюдений. Меньше — σ неустойчиво, сглаживание
не применять и прямо сказать в презе, что данных мало. Жёсткого стандарта на
порог нет: это инженерное правило, а не измеренный факт.
Результат проверь вторым срезом (например, исключением сглаженной точки).

### 5.4. Факт и прогноз — визуально разделять
Разные слайды или явная пометка в kicker («ФАКТ», «ПРОГНОЗ»). Ни одна расчётная
цифра не подаётся как измеренная.

### 5.5. Финальный слайд о точности
Прямо сказать, когда появится факт, и назвать условие: «точную величину можно
будет назвать после того, как пойдут реальные данные (пользователи, продажи,
период наблюдения)». Повторить ключевые цифры и условия их уточнения.

### 5.6. Персональные данные и обещания
В презентацию не попадают персональные данные клиентов (ФИО, телефоны, номера полисов,
договоров). Если они есть во входных данных — не копируй и сообщи об этом.
Нет формулировок, обещающих результат («гарантированно снизим»): эффект подаётся как
ожидание с уровнем уверенности. Не называй вывод уверенным, если уверенность средняя
или низкая.

## 6. Контент — только бизнес-результат
- Убирай технические детали (базы, таблицы, SQL, названия систем), если они не
  предмет презы. Если предмет — оставляй, но переводи в результат.
- Чистый русский, без сленга и англицизмов. Никаких «Отличный вопрос!».
- Главное — первым абзацем.

## 7. HTML-дека: сборка

Самодостаточный одиночный HTML: ни внешних скриптов, ни стилей, ни картинок — открывается
двойным кликом и переживает пересылку. Каркас — `assets/template.html`.

- Слайд 16:9: `aspect-ratio:16/9`, `width:min(100vw,177.78vh)`.
- Единица измерения — одна: `font-size: calc(min(100vw,177.78vh)/64)` на `.slide`, дальше
  всё в `em`. Тогда дека одинаково выглядит на любом экране.
- Пролистывание: `scroll-snap-type:y proximity` + навигация клавиатурой (стрелки,
  PageUp/Down, пробел) в скрипте шаблона.
- Режим отладки: открой файл с `?debug` — слайды, в которые не поместился текст, получат
  красную рамку, номера попадут в `window.__overflow` и в консоль. Исправляй переполнение
  сокращением текста или делением слайда, а не уменьшением шрифта.
- Печать в PDF без LibreOffice: `@media print` + `@page{size:1280px 720px;margin:0}`,
  фиксированный `font-size:20px`, `page-break-after:always`.

Готовый рабочий пример — `assets/example/`: `deck.html` (7 слайдов: титул, вывод, данные
и допущения, две находки, рекомендации, что дальше) и `facts.json` (14 фактов, из них 6
производных). На нём команда `check` даёт 0 ошибок и 0 предупреждений — сверяйся с ним,
когда непонятно, как оформить разметку. Пример в фирменной палитре.

Разметка (полное описание — `references/facts-and-markup.md`):

- Слайд: `<section class="slide" id="s3" data-title="…" data-role="finding" data-period="2026-09">`.
  Идентификаторы строго `s1…sN` по порядку.
- Число: `<span data-fact="cpa_search">…</span>` — внутри только текст, без вложенных тегов.
- Изменение с направлением: `<p data-trend="cpa_search_yoy_pct">CPA снизился на
  <span data-fact="cpa_search_yoy_pct">…</span></p>`.
- Не метрика (номер версии, количество шагов): оберни в `data-static`.
- Ссылка на слайд: `<a href="#s4">слайд 4</a>` — текст и номер в `href` совпадают.
- Оглавление: `data-agenda` на `ol`/`ul`; счётчик слайдов: `data-total-slides` (обновляет `sync`).

## 8. Реестр фактов и проверка

### Зачем реестр: доказательство на живом примере

Одно и то же число живёт на нескольких слайдах. В `assets/example/` CPA поиска «800 ₽»
встречается **2 раза** (KPI на слайде 2, таблица на слайде 4), а производный от него
разрыв с партнёрами «25%» — **3 раза**. Проверено запуском:

- поправить число **руками в одном месте** (800 → 750) → `check` даёт
  `E-FACT-TEXT`: «показывает 750 ₽, в реестре 800 ₽». То есть правка не завершена, и это
  видно машинно, а не «на глаз»;
- поправить то же число **в реестре** и запустить `sync` → обновлено **5 мест одним
  действием**, причём производный показатель пересчитался сам: разрыв с партнёрами
  «25%» → «33%» в трёх местах. После этого `check` — 0 ошибок.

Отсюда правило: **число правят в реестре, а не в деке.** Реестр — не бюрократия, а
единственное место, где число имеет одно значение; всё остальное в деке — ссылки на него.

### Формат

Реестр `facts.json` — единственный источник чисел. Поля: `label`, `value` или `derive`
(формула из `+ - * /`, скобок, чисел и id других фактов), `unit`, `decimals`, `scale`,
`signed`, `period`, `key` (обязателен на итоговом слайде и на слайде с данными).

```
python scripts/check_deck.py sync  deck.html facts.json          # подставить числа, обновить счётчик
python scripts/check_deck.py check deck.html facts.json          # проверить: 0 ошибок
python scripts/check_deck.py where deck.html facts.json <id>     # где факт и что от него зависит
python scripts/check_deck.py grep  deck.html "текст или regex"   # найти устаревшие формулировки
```

`check` ловит расхождения: число на экране против реестра, счётчик слайдов, ссылку в никуда,
оглавление против названий, текст ссылки «слайд N» против реального номера, остатки
заполнителей, внешние ресурсы, переполнение по лимитам, слово о росте против знака факта,
число, набранное руками без `data-fact`. Коды — в `references/facts-and-markup.md`.

### Протокол правок (обязательный, даже для «поменять одно слово»)

1. **Классифицируй правку.** Число → правь `facts.json`, а не HTML. Формулировка вывода,
   названия слайда или рекомендации → правка текста. Слайд добавлен/удалён/переставлен →
   правка структуры.
2. **Найди всё связанное до изменения.** Для числа — `where <id>`: где размечен, какие
   производные зависят, где то же число набрано руками. Для формулировки — `grep`:
   ищи старую фразу, её синонимы и соседние понятия (название канала, продукта, метрики).
3. **Внеси правку целиком.** Число — в реестре, затем `sync`. Текст — во всех найденных
   местах. Структура — перенумеруй `id="sN"`, `data-title`, оглавление, ссылки «слайд N»,
   затем `sync`.
4. **Проверь:** `check`. Любая ошибка = правка не завершена. Предупреждение
   `W-UNTRACKED-FACT` значит, что число набрано руками и снова разойдётся: оберни в `data-fact`.
5. **Перечитай то, что скрипт не видит:** следует ли вывод из данных на слайдах с находками;
   опирается ли каждая рекомендация на существующую находку; относятся ли допущения к
   оставшимся выводам; совпадают ли названия каналов, продуктов и метрик во всех слайдах.
   Полный список — `references/consistency-checklist.md`.
6. **Сообщи пользователю**, что изменено и где: числа (старое → новое, сколько мест
   обновилось), тексты (какие слайды затронуты), что осталось на его решение.

## 9. Ветка PPTX (python-pptx)

Когда результат нужен файлом .pptx, а не HTML:
- Формат 16:9: `slide_width = 12192000`, `slide_height = 6858000` EMU (13,33×7,5″).
- Пустой макет: `prs.slide_layouts[6]`; свои подложки/карточки — фигуры
  `ROUNDED_RECTANGLE`/`RECTANGLE`.
- Отключить тень у фигур: `shape.shadow.inherit = False` — иначе pptx добавляет
  свою и вид становится шаблонным.
- `RGBColor.from_string` НЕ принимает `#` — передавай hex без решётки
  (хелпер: `str(v).lstrip('#')`).
- Графики — matplotlib в PNG (dpi 100–170), затем `add_picture`.
  `bbox_inches='tight'`, `facecolor='white'` — иначе белые поля вокруг
  прозрачного фона.
- Отсутствие LibreOffice/PowerPoint = нет конвертации в превью. Честно сказать
  пользователю, что визуально рендер не проверен, а проверен программно.
- Если файл открыт в просмотрщике, `prs.save` даст `PermissionError` — сохраняй
  под новым именем и сообщи об этом.
- `check_deck.py` проверяет HTML, не PPTX. Для PPTX числа сверяй по реестру вручную
  или выгружай из `facts.json`.

## 10. Финальные ворота перед выдачей

- `check` показывает 0 ошибок; оставшиеся предупреждения объяснены пользователю.
- Пройден чек-лист чтением (`references/consistency-checklist.md`).
- Нет персональных данных и заполнителей (фигурные скобки, заглушки).
- Файл самодостаточный: без внешних скриптов, стилей и картинок.
- Контраст текста к фону: WCAG AA, для заголовков — AAA.
- Заголовки/цифры не наезжают на подписи и на график (см. §3).
- Визуальный элемент есть на каждом содержательном слайде.
- Файл открыт с `?debug` (если есть доступ), переполненных слайдов нет.
- Суммы на титуле и финале совпадают с расчётными.
- Пользователю сообщено: что изменено, что проверено (скриптом и чтением), что осталось
  допущением, какие рекомендации требуют согласования.

Если скрипт нельзя запустить (нет Python или доступа к файлам), честно скажи об этом и
выполни ручную проверку по чек-листу: пройди каждый `data-fact`, каждое число в тексте и
каждую ссылку на слайд. **Не заявляй «проверено скриптом», если скрипт не запускался.**

## 11. Чего не делать

- Не вписывать числа в HTML вручную мимо `facts.json`.
- Не править только то место, на которое показал пользователь.
- Не менять `h2` без `data-title` (и наоборот) и не копировать слайд, не обновив `id` и ссылки.
- Не писать в заголовках числа и сравнения, которые может опровергнуть правка данных.
- Не скрывать предупреждения скрипта и не отключать проверки ради «зелёного» результата.
- Не выдавать презентацию при ошибках `check`.
- Не уменьшать шрифт, чтобы влез текст: сокращай текст или дели слайд.
- Не использовать цвет из палитры графиков как цвет оформления и наоборот.
